# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Project Is

**midigpt-LIVE** is a Max for Live device (`patchers/MIDI-GPT.amxd`) that generates MIDI in Ableton Live with the **MIDI-GPT** model. The device reads clips from the selected scene, sends them as context to a MIDI-GPT HTTP server, and writes the generated notes back into clips.

Targets: macOS (Windows partly), Live 11+ (Max 8.6) and Live 12 (Max 9).

The device is built by scripts: `tools/build_device.py` (re)builds `patchers/MIDI-GPT.amxd` in place (panel window, strip key, dependency list) and `tools/build_tag_device.py` writes `patchers/MIDI-GPT Instrument.amxd`. Edit the scripts, assets or build scripts, then rebuild; don't hand-edit the `.amxd` files.

> **History:** the original MMM4LIVE device embedded the MMM model through a C++ external; that was replaced by the MIDI-GPT HTTP client in `37e3cfa`, and the old window and Ember prototypes were removed when the panel replaced them. The scenes × tracks × bars state model in `midigpt.js` is inherited from it.

## Running

1. Start a server: `midigpt-http --pretrained yellow_medium --port 3456` in a venv with `midigpt[http,inference]` (or `install.sh --server`, see Deployment). A remote server works too; its URL goes in the device's SETUP page.
2. Rebuild (`python3 tools/build_device.py`) and drag `patchers/MIDI-GPT.amxd` onto a track in Live; click the key on the device to open the window.

There are no automated tests. Use `tools/maxtool.py validate` for patches and the dev bridge for behaviour (both below).

## Architecture

```
patchers/MIDI-GPT.amxd              the device: js midigpt.js, node.script, dev bridge, "p main_window" (the panel), strip key
patchers/MIDI-GPT Instrument.amxd   the per-track instrument tag
javascript/
  midigpt.js              core: Live API observers, state, HTTP client, writing clips; include()s midigpt_panel_link.js
  midigpt_panel_link.js   panel side of the core: panel_state / panel_notes pushes, panel_message(), faults
  midigpt_panel.js        the panel (jsui, 5 instances: one per region, jsarguments = region name)
  midigpt_canvas.js       canvas-2D shim over mgraphics (include()d by midigpt_panel.js)
  midigpt_panel_spec.js   generated by tools/export_panel_assets.py: layout + theme
  midigpt_strip.js        the device strip in Live's chain: one key that opens the window
  midigpt_tag.js          face of the tag device (readout + Family / Program menus)
  midigpt_node.js         Node for Max: open the tag device in Live, per-user settings file
media/panel/midigpt_*.png rendered lo-fi assets (export_panel_assets.py from tools/frontend_assets.py + render_ui.py)
```

midigpt.js outlets: 0 → the window (`panel_state <json>`, `panel_notes <json>`), 1 → the dev bridge's `udpsend`, 2 → `node.script midigpt_node.js` (`open_tag`, `config_set`). Its inlet takes `panel <verb> ...` from the panel (`panel_message()`), `server_url <url>` from the address field, `tag_changed` (from `[r midigpt_tag_changed]`), and `config <key> <value>` / `node_error` from the helper (`handle_message()`).

The panel window is 960 x 640, split into region jsuis (top, roll, main, output, masks) so each repaints only when its own `regionKey()` changes; page backgrounds are fpics shown/hidden by page. The server address is a native `textedit` (`setup_url`) over the SETUP screen. Pushes start when the panel says `ready` (`panel_ready`).

mgraphics gotchas met while building the panel: `image_surface_draw` paints through the current path and with the current source alpha (call `new_path()` and `set_source_rgba(1,1,1,1)` first); group alpha (`push_group`) shifts output, so dimmed parts are pre-dimmed sprites (`_aNN`); Max caches `require()`d modules, so edited modules are `include()`d; `open` is a built-in jsui message (never name a function `open`). Keep these scripts ES5.

Takes: before the first take is written, `snapshot_targets()` saves each target clip; `take -1` restores it and Keep commits the selected take. **Only use the Live 11 note API** (`get_notes_extended`, `remove_notes_extended`, `add_new_notes`): the old one makes Live block the device with a "uses an older process to modify MIDI notes" dialog. Only the generated bars are rewritten, and each bar's notes are sent sorted by onset.

Model facts the UI depends on: density is drum-only on the current checkpoints (the server 422s otherwise); pitch range only applies with scale lock on; remix replaces the rhythm grid; top-p must be in (0, 1].

### Server API (MIDI-GPT HTTP)

`GET /health`, `GET /info` (capabilities, `model_dim_options`), `GET /models`, `POST /generate` (body: `score`, `request`, `request_id`, `model`), and `POST /generate/<id>/cancel`. `/health` is polled every 15 s.

### Startup

`live.thisdevice → deferlow → "init"` calls `init()` exactly once. Top-level script code only declares state. Anything that touches the Live API, the network or on-disk config starts in `init()`, because `this.patcher.filepath` (used to find the repo root) is often still empty while the script is first being instantiated.

## Performance rules (learned the hard way)

- **Only real performance controls are Live parameters.** Anything driven by JS uses `parameter_invisible: 2` (Hidden), or every JS `set` becomes a Live parameter write: automation, undo history and set size all grow with it. A device's `parameters.parameter_overrides` block overrides what a subpatcher says.
- **Create Live API observers once**, then retarget them with `.id = …` **followed by re-setting `.property`**: that is what fires the callback once with the new object's value (without it the clip length is never read). Creating a new observer per selection leaks them.
- **Don't walk the Live set on clicks.** `panel_scene()` caches the scene's tracks, clips and notes until a selection, clip, track or scene change invalidates them (`invalidate_scene_cache()`).
- **Dict writes are coalesced** (`schedule_dict_sync`, 100 ms). The dicts only exist so state survives a script reload.
- **Prefer one widget over many objects.** Moving or recolouring dozens of `live.*` objects with scripting redraws each one separately; the panel is a few jsuis for that reason. Native `live.*` widgets where they fit (the tag's menus): relabel a `live.menu` / `live.tab` with `_parameter_range`.
- **Box order in a patch file is z-order, front first.** A box added at the end of `boxes` draws *under* every panel before it; insert UI on top at index 0.
- `textedit` takes `set <text>` to show text without output; it has no `settext` message.
- **Logging is free when off.** `flog()` and the file log only run in dev mode; the file log is buffered and flushed at most once a second.
- Max's `File`: `eof` is the file **length**, not a flag, and `"write"` mode does **not** truncate. Settings files are written by the Node helper instead.

## Tools

```bash
python3 tools/maxtool.py validate patchers/*.amxd         # structural checks
python3 tools/maxtool.py params   patchers/MIDI-GPT.amxd   # Live params + visibility
python3 tools/maxtool.py tree     patchers/MIDI-GPT.amxd
```

`tools/maxtool.py` is also a library (`load`, `save`, `walk`, `find_box`, `validate`). **Always edit `.amxd` / `.maxpat` through it**: it keeps the `.amxd` binary header and length field correct, and writes JSON byte-identical to Max's own formatting so diffs stay reviewable. For edits that add or rearrange many objects, the `generate-maxpatch` / `explain-maxpatch` skills (maxpylang) and py2max are also installed. Write patch changes as idempotent build scripts (like `tools/build_device.py`) and validate before saving.

### Dev bridge: driving the running device

Enable it with `touch .midigpt_dev` in the repo root (gitignored), then load or reload the device in Live or the Max editor. Without that file the bridge only answers "dev mode off".

```bash
python3 tools/bridge.py state                     # selection, server, current track params
python3 tools/bridge.py ui                        # every named widget: value, rect, hidden
python3 tools/bridge.py msg panel generate            # what the panel sends
python3 tools/bridge.py msg set_global_param temperature 0.8
python3 tools/bridge.py eval 'current_track'      # evaluate in midigpt.js scope
python3 tools/bridge.py reload                    # recompile midigpt.js from disk + init
python3 tools/bridge.py log 50                    # tail midigpt.log
```

`autowatch` is off in every script, so use `reload` after editing `midigpt.js`. Other scripts (and the jsui files) reload when the device is reloaded.

### Screenshots and clicks

`tools/screen.sh windows | shot <png> [app] [title] | click x y | front <app>`. It needs Screen Recording + Accessibility permission for the terminal, and `cliclick`. Only windows on the current Space are listed/captured, so bring Live or Max to the front first; a sleeping display makes captures fail and pauses the device.

`tools/live_reload.sh [track] [file]` reloads the device inside Live after patch edits: it deletes itself through the bridge and Live re-inserts the device file, then the window is opened.

`tools/live_reload.sh` closes the old instance's window first: Live keeps a deleted device alive for Undo, and its window (and script) would otherwise linger.

`tools/max_reload.sh` quits Max cleanly (`quit saving no`) and reopens the device standalone, waiting for the bridge. Never `kill -9` Max: it triggers "Recover edits?" on the next launch. Don't run the device in Max and Live at once; both bind UDP 7474.

## Track instruments: the MIDI-GPT Instrument tag

A track's GM instrument is stored ON the track, in a tiny pass-through MIDI effect, `patchers/MIDI-GPT Instrument.amxd` (built by `tools/build_tag_device.py`; one stored parameter "Instrument": GM 1-128 or Drums). It is saved with the set and follows the track through renames, reordering, duplication and copy/paste: the Live counterpart of the Reaper plugin renaming tracks to canonical instrument names. midigpt.js finds it by device name (`find_tag`, `read_tag`, `write_tag`).

A track without a tag is detected from what Live exposes, in this order only (`detect_track_instrument`): its instrument device (a Drum Rack means drums, otherwise the device/preset name), then the track name, else Acoustic Grand Piano. Names are matched with the Reaper plugin's keyword table (`GM_KEYWORDS`, exact canonical names first), so both plugins resolve names identically.

The Live API cannot insert devices. `ensure_tag` selects the track and sends `open_tag <device folder> <file>` to `javascript/midigpt_node.js` (Node for Max), which asks the running Live to open the file (Live loads it onto the selected track); midigpt.js then polls for the device and sets it.

Setup: SETUP ALL / SETUP SEL ask for detection (auto, or confirm each); then each track that needs it is confirmed in the instrument browser and tagged. Setup only writes tags: the device ships no synth or SoundFont, and tracks keep their own sounds.

## Deployment

Users install with `bootstrap.sh` (curl one-liner) -> `install.sh`: the release zip goes into `<User Library>/MIDI-GPT/` (path read from Live's `Library.cfg`), and, if asked, a server venv in `~/Library/Application Support/MIDI-GPT/server` (uv when available, else Python 3.10-3.12 + pip; `midigpt[http,inference]` pinned) with `start-server.sh` (port 3456, 127.0.0.1) and a `Start MIDI-GPT Server.command`. `--uninstall` removes it all. Tested in a sandboxed HOME on macOS (uv and pip paths); not on Linux; no Windows installer yet.

Releases: `python3 tools/build_release.py` -> `dist/MIDI-GPT-for-Live-<VERSION>.zip`, both devices frozen by `tools/amxd_freeze.py` (no Max needed; re-packs 164/166 of the frozen devices on this machine byte-identically) with include()/require() inlined. Attach it to a GitHub release `v<VERSION>`.

Per-user settings (server URL, install dir) are in `~/Library/Application Support/MIDI-GPT/live.json`, read and written by `midigpt_node.js` (`config_set`, `config <k> <v>` on start); a frozen device's folder may be read-only. The tag device is opened by `open_tag <device folder> <file>`: next to MIDI-GPT.amxd, then the saved install dir, then `~/Music/Ableton/User Library/MIDI-GPT/`.
